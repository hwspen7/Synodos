# Meeting knowledge implementation and acceptance protocol (2026-11-05)

## What the Meeting knowledge branch implements

- PostgreSQL AI jobs, current-revision knowledge records, source segment IDs,
  millisecond timestamp provenance, and model version attribution.
- Server-side cursor retrieval across all eligible chunks. No historical
  recent-250 truncation. The current embedding backend stores JSONB float
  arrays and does an **exact O(N) similarity scan**. No pgvector or approximate
  nearest-neighbour index is implicitly available. This is a correctness-first
  local implementation; latency at large corpus sizes needs explicit testing.
- Multilingual lexical token coverage, including CJK and Hangul bigrams.
  Embeddings improve semantic recall when a separate local embedding model
  has been installed and enabled.
- Optional scoped meeting IDs in `/api/intelligence/search`, `/ask` and
  `/ask/evidence`. The Knowledge Center UI now scopes to the currently viewed
  meeting by default. Searching all local meetings/media requires opt-in.
- Embedding vectors are scored only against the matching embed-model name.
  Changing the configured embedder requires reindexing meetings to gain the
  new vector retrieval benefit.
- Revision-aware writes use PostgreSQL row-level locking and compare-and-swap.
  Stale knowledge is invisible to retrieval. A transcript changed during
  inference blocks the generated quote response. Completed historical
  evidence-job results are masked if their meeting source revision changes.
- Quote selection runs through a bounded Ollama JSON schema with `think=false`
  for evidence jobs only. Every accepted quote must be an exact substring
  of a source chunk. Invalid or unverified model output is discarded.
- The QA result is **source-verbatim evidence**, not independent truth or
  semantic entailment verification. Automatic external actions remain disabled.

## Verifications completed in GitHub Actions

The pull request runs three independent workflows: project validation,
operations safety, and Windows launcher validation. Project validation
includes backend unit tests, frontend type-check/build and a PostgreSQL 17
service integration suite. The new integration suite exercises real database
row versions, index replacement, source scopes, job state, and mock-model
JSONB embeddings. A separate fixture suite checks 36 answerable prompts and
six negative cases for coverage and correct expected answers.

No CI workflow can access the user's E-drive Saluki weights, local Ollama,
real meeting corpus, microphone, or human judgment. Mock embedding
tests cannot establish actual Qwen embedding quality, and exact quote
matching cannot prove spoken factual truth.

## Local 12-language model acceptance

The actual local runner requires the currently configured
`DATABASE_URL` pointing **exactly** to `meeting_test`, a running
PostgreSQL 17 server, and Ollama port 11434 with Saluki 27B installed.
Do not paste passwords, URLs with credentials, or private transcripts
into issue logs.

From a PowerShell session already containing `DATABASE_URL`:

```powershell
cd E:\Meeting-Fixed10-Test
git fetch origin feature/meeting-knowledge-quality
git merge --ff-only FETCH_HEAD

& .\tools\Invoke-Meeting-Knowledge-Acceptance.ps1
```

The launcher only uses the test database, writes results under
`E:\AI-Cache\MeetingResults`, and cleans its own isolated
`knowledge_eval_...` meeting IDs. It does not delete previous user
meetings, automatically download models, or change the live backend.

- If the embedding model `qwen3-embedding:0.6b` is missing, install it
  into the user's configured E-drive Ollama model store before repeating
  the hybrid run. The lexical acceptance still runs, but full release
  acceptance is **not passed** without a successful hybrid run.
- Reports are `meeting_knowledge_lexical.json` and `meeting_knowledge_hybrid.json`.
  Each includes model names, test questions, expected fields, result
  verdicts, abstentions, and observed latency p50/p95.
- Both modes must pass all 36 positive and six negative cases independently
  before claiming the **synthetic local model** gate is passed.
- No single short fixture can certify 12-language real-world retrieval
  recall, semantic correctness or hallucination rates. At least one
  independently annotated and held-out real meeting corpus is needed.

## Remaining release gates outside CI

The following evidence is not generated by this GitHub branch:

1. Run both real Saluki and embedding evaluations from the user's E-drive.
   Archive JSON outputs with exact model tags and no credentials.
2. Score at least 20 *real* meeting questions against human-selected source
   timestamps, including positive answers, valid refusals, contradictions,
   stale revisions and cross-meeting attribution.
3. Repeat multilingual tests on actual recordings rather than synthesized
   captions. Report retrieval Recall@k, citation precision, answer correctness,
   abstention precision and per-language sample counts.
4. Record end-to-end p50/p95 on the user's RTX host and evaluate index/query
   latency on a realistic full corpus. Exact JSONB vector scan is O(N).
5. Do not conflate the Meeting knowledge knowledge and evidence gates with the
   separate Phase 1 overlap-inclusive acoustic DER release gate (21.77%
   versus frozen target 20%) or Phase 2 independently human-verified
   speaker identity holdouts; those remain separately outstanding.

Status must distinguish `code_and_database_ci_pass`,
`local_synthetic_model_pass`, and `real_meeting_release_pass`.
No main-branch merge is warranted solely from deterministic CI checks.
